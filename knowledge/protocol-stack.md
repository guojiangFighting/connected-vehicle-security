## 1. 总原则：先拓扑，再字典，后字段

协议分析最常见的失败模式是「一上来扫端口 / 盲发 UDS」。车内通信是**按域隔离的多总线系统**，正确顺序是：

```text
物理接入点（端子 / OBD / 以太网口 / 无线）
        │
        ▼
网络拓扑（网关 + 域：Diag / TBOX / 底盘 / 车身 / 信息 / 能量 …）
        │
        ▼
协议「字典」（DBC / LDF / ODX / ARXML / Fibex …）
        │
        ▼
分层还原（物理层 → 传输层 → 应用层 / 服务）
        │
        ▼
信任边界与滥用用例（伪造、重放、跳步、未授权服务）
```

黑盒要自己逆向补齐的三类情报（整车渗透文明确点名）里，有两类直接是协议向的：

1. **IPC / RPC 通信方式**（进程间、组件间怎么说话）
2. **私有协议字段定义**

第三类 **OTA 升级包分发** 则跨「云协议 + 车内刷写协议」。

## 2. 车内协议栈分层图（分析用）

不必死记标准编号，按「你在哪一层动手」理解：

```text
┌─────────────────────────────────────────────────────────┐
│  业务 / 应用                                             │
│  远程控车 · OTA · eCall · 监管上报 · 诊断例程 · 私有 RPC  │
├─────────────────────────────────────────────────────────┤
│  应用层协议                                              │
│  UDS (ISO 14229) · SOME/IP · 厂商私有 TLV/Protobuf       │
├─────────────────────────────────────────────────────────┤
│  会话 / 传输适配                                         │
│  ISO-TP (ISO 15765) · DoIP (ISO 13400) · SoAd / TCP-UDP  │
├─────────────────────────────────────────────────────────┤
│  网络 / 总线                                             │
│  CAN / CAN-FD · LIN · FlexRay · 车载以太网 (100/1000BASE-T1) │
├─────────────────────────────────────────────────────────┤
│  物理接入                                                │
│  OBD · 域内接头 · 网关镜像口 · TBOX 蜂窝/Wi-Fi/BT         │
└─────────────────────────────────────────────────────────┘
```

**分析含义**：

| 你卡在哪层 | 典型动作 |
|------------|----------|
| 物理 / 端子 | 找电源、CAN-H/L、Eth、UART；确认接的是哪个域 |
| 总线 | 抓帧、看波特率/仲裁 ID、域间是否经网关过滤 |
| 传输 | 拼长帧（ISO-TP）、找 DoIP 端口与路由激活 |
| 应用 | 会话切换、安全访问、DID/例程、服务发现 |
| 业务 | 控车指令、OTA 验签、监管数据路径 |

## 3. 第一步：从插线端子还原「协议在哪跑」

来源：[从插线端子分析车内通信网络结构](https://delikely.eu.org/2021/11/18/Vehicle-Cable-Connection-Terminal/)

网关把内部 CAN 等划成多个域，例如：

| 域 | 典型节点 | 协议分析重心 |
|----|----------|--------------|
| DiagBUS | 诊断通路 | UDS on CAN / DoIP 入口、OBD |
| TBUS | T-BOX | 远程业务经网关进车内；外网协议 + 内网转发 |
| CBUS | ABS / EPB / EPS 等 | 安全相关报文；伪造影响大，通常要先有入口 |
| EBUS | BCM / PEPS / TPMS / DVR 等 | 车身执行器；「旁路节点 → 同域横移」 |
| IBUS | 车机 / 仪表 / 空调 | 信息娱乐与座舱；常与车机落点同域 |
| EVBUS | BMS / OBC / 电机等 | 充放电与动力；充电桩链路交叉 |

**安全向思路**（原文思考点）：

- 黑盒物理分析常从**端子找供电与总线针脚**开始。
- 不一定只打 TBOX/IVI：例如 DVR 挂在车身域 CAN 上，拿下后可能同域影响 BCM（门锁/灯光等）。
- 域隔离靠网关：**分析重点 = 网关转发规则 + 谁信任谁的报文**。

## 4. 第二步：用数据库文件当「协议字典」

来源：[汽车数据库文件](https://delikely.eu.org/2024/11/15/automotive-DB-file-set/)

车载系统、售后工具、供应商交付物里常残留描述文件。拿到字典 ≈ 把黑盒协议变成灰盒。

### 4.1 按用途分类

| 类型 | 格式 | 分析价值 |
|------|------|----------|
| 网络通信 | **DBC**、LDF、FIBEX、DBF | CAN/LIN 消息 ID、信号布局 → 可解码 / 构造合法帧 |
| 诊断 | **ODX**、PDX、CDD、DEXT | UDS 服务、DID、DTC、刷写序列 → 诊断用例与后门 DID |
| 架构 | **ARXML** | AUTOSAR 组件、通信接口、端口 → 服务拓扑与信任边界 |
| 标定 | **A2L** | 测量/标定变量地址 → 敏感参数面（偏研发/台架） |

### 4.2 字典驱动的分析顺序

```text
搜残留（车机/TBOX 文件系统、售后包、泄露企标）
  → 识别格式（dbc / odx / arxml / ldf …）
  → 抽出：高权消息、写类 DID、刷写相关服务、跨域信号
  → 对照实车流量做差异分析（文档有、线上无；线上有、文档无）
```

**渗透文提醒**：企标、DID、27 算法库等 OSINT，本质也是在补「协议字典」。

## 5. 按协议族拆解的深入分析思路

### 5.1 CAN / LIN：信号层

**目标**：搞清「谁发什么、谁信什么」。

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 拓扑确认 | 端子 / 原理图 / 网关域 | 你挂的是哪条总线 |
| 被动捕获 | 正常工况 + 关键操作（开门、刹车、换挡） | ID 频率表、候选控制帧 |
| 对照字典 | DBC/LDF 映射信号 | 可解释的信号表 |
| 无字典时 | 差分（操作前后）、周期/事件分类、固件里找打包代码 | 粗粒度语义 |
| 信任检验 | 同 ID 多源？网关是否过滤？接收方校验否？ | 伪造 / 注入可行性结论 |

**与灰黑盒衔接**：总线信任滥用通常需要**先有落点**（车机/TBOX/同域弱节点），再谈注入。

### 5.2 ISO-TP + UDS：诊断与刷写

来源：[UDS 刷写](https://delikely.eu.org/2023/05/01/UDS-flash/)、[OBD-II 标准阅读](https://delikely.eu.org/2021/04/29/2021-WIDC%E4%BF%A1%E6%81%AF%E5%AE%89%E5%85%A8%E6%8C%91%E6%88%98%E8%B5%9B%E9%A2%84%E8%B5%9B%E5%9B%9E%E9%A1%BE%E4%B8%8EOBD-II%E5%87%86%E9%98%85%E8%AF%BB/)

承载关系：

```text
OBD / 诊断 CAN  ──ISO-TP──►  UDS
车载以太 / IP   ──DoIP  ──►  UDS
```

**刷写流程（分析骨架）** 常见服务链：

| 服务 | 含义 | 安全检查点 |
|------|------|------------|
| 0x10 | 会话控制 | 是否可随意进编程会话 |
| 0x27 | 安全访问 | 种子质量、算法可逆、常量复用、锁定/Reset 旁路 |
| 0x28 / 0x85 | 通讯控制 / DTC 设置 | 刷写时停通讯是否可被恶意利用 |
| 0x31 | 例程控制 | 前置条件检查、编程依赖校验是否可骗过 |
| 0x34 / 0x36 / 0x37 | 下载 / 传数 / 退出 | **是否强制先过 27**；通道是否明文可嗅探 |
| 0x11 | 复位 | 刷后生效；是否可打断锁定计数 |

**深入分析逻辑**：

1. **流程完整性**：缺哪一步仍能刷？能否跳过 27 直接 34/36？
2. **算法与密钥**：固件 / 诊断仪逆向 Seed2Key；跨 ECU 共用常量。
3. **会话与状态机**：扩展会话 ↔ 编程会话切换条件；低权限服务穿插。
4. **通道机密性**：CAN 明文下载 = 旁听即可拿固件。
5. **应用层旁路**：远程诊断 / TSP 侧是否绕过车内 27 直接调敏感能力。

灰盒有 ODX/CDD 时：直接按文档列服务清单做**负向用例**（乱序、重复、超长、错误会话）。

### 5.3 DoIP / 车载以太网：诊断上 IP

分析顺序建议：

```text
发现 DoIP 实体（端口 / 组播 / 路由激活）
  → 逻辑地址与实体表
  → 再跑 UDS（同上）
  → 额外看：未激活能否诊断、跨 VLAN/域路由、TLS 有无
```

与 CAN 诊断对比：IP 路径更容易从**已失陷的车机/TBOX** 横向扫到，而不必物理搭线。

### 5.4 SOME/IP：服务发现与 RPC

来源提示：[Android 车机跑 Python](https://delikely.eu.org/2023/11/16/pydroid/)（整车隔离网里用 Scapy 测 SOME/IP）

| 步骤 | 关注点 |
|------|--------|
| 服务发现 | 谁在广播 Offer；未授权能否 Subscribe |
| 方法 / 事件 | 参数校验、鉴权、是否信任来源 IP/MAC |
| 测试位置 | 域隔离导致笔记本直连失败 → 在车机侧跑脚本更稳 |
| 与私有 RPC | 很多「私有协议」实为 SOME/IP 之上或平行的厂商栈 |

黑盒必做：在固件里搜服务名、端口、序列化格式，还原 **IPC/RPC 字段**（渗透文三类情报之一）。

### 5.5 TBOX ↔ 云 / App：外网与私有协议

来源：[TBOX 主要功能](https://delikely.eu.org/2021/08/15/TBOX-Main-Function/)、[大众 OCU](https://delikely.eu.org/2021/09/29/VW-OCU/)

TBOX 业务即协议面：网络接入、OTA、远程控车、定位、eCall、远程诊断、国标监管（如 GB/T 32960）等。

**分析双轨**：

| 轨 | 思路 |
|----|------|
| 外→内 | App/TSP API、证书钉扎、重放、指令鉴权 → 能否下发控车/诊断 |
| 内→外 | 抓蜂窝流量、逆向客户端 → 包格式、密钥、OTA URL |
| 内→车 | TBOX 落点后经 CAN/Eth 转发；看网关是否当「可信节点」 |

每条业务对应四类滥用：**伪造指令 / 窃听 / 篡改 / 可用性破坏**。

### 5.6 OTA：跨层协议链

```text
云端分发协议（HTTPS/私有）
  → 包格式与元数据（版本、差分、签名块）
  → 车端验签与安装器
  → 可能再转 UDS/私有刷写打到其他 ECU
```

分析重点：找包来源（平台洞、测试包、明文截取、逆向下载地址）→ 验签是否可绕 → 或从包反推他 ECU 升级逻辑。  
另：升级策略本身可造成**可用性/人身安全**类风险。

### 5.7 无线：蜂窝 / Wi-Fi / BT / GNSS

| 面 | 协议分析切入 |
|----|----------------|
| 蜂窝 | 降级、APN 进内网后的横向；模组 AT 口/AT 残留 |
| Wi-Fi / BT | 配网模式、协议栈 CVE、弱初始凭证 |
| GNSS | 欺骗对业务（定位/电子围栏）的影响；多模则威胁降 |

这些面常作为**进 TBOX/车机的第一跳**，再进入 5.1–5.5 的车内协议。

### 5.8 充电：桩—车—云交叉

来源：[充电桩漏洞挖掘](https://delikely.eu.org/2022/04/29/chargebox-vuln-hunter-garo-and-bender/)

协议视角：公网管理协议 + 充电控制协议 +（可选）车端充电 CAN。  
选靶逻辑仍是：公网可达 + 固件可得 → 先静态拿账密/升级接口，再动态度量业务 API。

## 6. 一条可复用的「协议深入」工作流

结合整车渗透「信息收集 → 威胁建模 → 静动态挖洞」：

```text
① 定接入点     端子 / OBD / 车机网卡 / TBOX 无线
② 画域与网关   哪些 ECU 同域、谁转发
③ 收字典       DBC/ODX/ARXML/企标/固件字符串
④ 分层抓包     总线原始帧 → 解传输 → 解应用
⑤ 建状态机     会话、安全访问、服务发现、业务指令
⑥ 负向用例     跳步、重放、越权 DID、畸形长度、错误来源
⑦ 静动对照     固件里打包/解包代码 ↔ 线上真实流量
⑧ 写边界结论  哪一层缺认证/加密/过滤 → 链到执行器或数据
```

**静动对照**特别重要：文档说有签名，流量里看不到验签往返 → 优先深挖实现差异（灰盒逻辑）。

## 7. 黑盒 vs 灰盒：协议分析怎么分岔

| 目标 | 黑盒 | 灰盒 |
|------|------|------|
| 解 CAN 信号 | 抓包差分 + 固件逆向打包 | 直接吃 DBC/LDF |
| 打 UDS | 扫服务 → 提固件破 27 | ODX/算法文档驱动用例 |
| SOME/IP / 私有 RPC | 逆向字段与端口 | ARXML / 接口说明列方法表 |
| OTA | 截流 / 逆向客户端 | 按设计文档构造乱序与非法包 |
| 域横移 | 落点后扫总线与开放服务 | 按 EE 架构选高价值旁路节点 |

原则不变：**灰盒缩小搜索空间，黑盒手段验证与补洞**。

## 8. 协议向攻击链模板（与灰黑盒文档对齐）

| 链 | 协议路径 |
|----|----------|
| A | 外设/车机落点 → 同域 CAN/Eth → 执行器相关报文 |
| B | 调试/半开 → TBOX → 云协议或转发进 TBUS/网关 |
| C | 字典/固件 → 弱 27 → UDS 34/36 或明文嗅探固件 |
| D | 公网桩管理协议 → 升级/控制面 → 供应链扩散 |
| E | 业务抓包 → 监管/跨境数据协议路径（合规向） |

## 9. 防御对照（协议层最小集）

| 协议层问题 | 防御方向 |
|------------|----------|
| 总线盲信 | 网关过滤、关键信号认证/MAC、域隔离 |
| 弱 27 / 可跳过刷写 | 真随机、锁定、强制安全访问、HSM、非对称 |
| 明文诊断/刷写 | 加密通道；敏感 DID 保护 |
| 私有 RPC 无鉴权 | 服务端鉴权、最小暴露、证书体系 |
| OTA 验签可绕 | 安全启动链 + 不可跳过验签 |
| 字典残留 | 量产镜像清理 DBC/ODX/密钥材料 |

更全对照见 `checklist.md`。
